# Native policy refresh

Native policy files are loaded into immutable service runtimes. Editing the configured file does not refresh the loaded policy. `native policy-refresh plan` reports the exact loaded and candidate digests, runtime generation and paused revision. Save that JSON, review it, then use `native policy-refresh apply --plan <file> --reason <text>` through the authenticated native gateway.

This first version requires an explicitly paused board and rejects board, repository, base branch or agent topology changes. It rejects in-flight native calls, active leases, uncertain effects, runnable Workboard cards, incomplete session listings and accepted runs without terminal proof. It does not cancel workers, alter cron schedules, delete evidence or resume execution. Both runtime registries switch together while retaining the same evidence store and pause revision. Stale plans must be regenerated.

Each idle proof requests up to 1,000 sessions per page and accepts at most 10,000 sessions across at most 50 requests. Oversized responses, changing totals, duplicate identities and invalid cursors still reject the refresh. Short pages are allowed when their cursor and total remain consistent. Both complete idle proofs remain required; larger pages reduce listing calls without asserting a particular refresh duration.

The configured candidate must pass doctor checks. A changed investigation skill/policy binding remains paused until the existing protected evaluation and promotion process approves its exact digests. Controlled authority/compatibility evaluations do not establish semantic quality. Resume checks the active binding again. The gateway doctor RPC reports the loaded policy digest and skill binding; the standalone CLI doctor validates the file on disk.

Policy refresh changes policy data only. Updated JavaScript, plugin registration or gateway configuration still requires its supported deployment lifecycle. Service shutdown fences new calls and drains existing calls before closing the store. No private gateway reload APIs are used.

Historical Workboard cards may have their current execution association cleared through the public card update API while their accepted launch and attempt history remain. Refresh accepts this only when all current association fields are absent/null, the complete accepted/requested/provisional identities agree, and one exact terminal attempt matches. The matching inactive terminal session must end after both the attempt start and launch acceptance. Attempt `endedAt` must be valid but is not the execution clock: Workboard rewrites it from a terminal execution update timestamp, including later operator bookkeeping. Partial or contradictory associations, duplicate attempts, and missing session evidence still block refresh.
